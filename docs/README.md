# 项目开发与协作框架（Docs Index）

> 本目录是项目的"制度层"。代码解决"怎么做"，这里解决"为什么这么做、按什么顺序做、做完留下什么"。
> 原则：**流程为工程服务，而不是绑架工程**。所有流程都可以按体量裁剪，但记录不可省略。

## 目录结构

```
json-on-sql/
├── BUGLOG.md              # Bug 修复日志（根目录，独立维护）
├── CHANGELOG.md           # 版本变更日志（用户可感知的功能/修复变化）
└── docs/
    ├── README.md          # 本文件：框架总览与索引
    ├── PROCESS.md         # 标准工作流程（完整流程 + 轻量通道）
    ├── STANDARDS.md       # 项目约定（编码规范、命名、验证清单）
    ├── ROADMAP.md         # 路线图（想法池 → 排期）
    ├── decisions/         # ADR 架构决策记录（为什么这么做）
    │   ├── TEMPLATE.md
    │   ├── ADR-001-双语国际化架构.md
    │   ├── ADR-002-英文主体SEO策略.md
    │   └── ADR-003-SQL点语法与表名解析.md
    └── reviews/           # 头脑风暴 / 复盘记录（讨论过程与结论）
        └── TEMPLATE.md
```

## 各文件的分工（谁记录什么）

| 文件 | 回答的问题 | 什么时候写 |
|---|---|---|
| `decisions/ADR-xxx.md` | **为什么**这么做？当时考虑了哪些方案？ | 做出重要技术/产品决策时 |
| `reviews/*.md` | 讨论过程、头脑风暴、正反方观点、结论 | 有实质性讨论发生时 |
| `CHANGELOG.md` | 这次改了什么（用户视角） | 每次功能/修复落地后 |
| `BUGLOG.md` | 这个 bug 是怎么回事、怎么防再犯 | 每次修 bug 后 |
| `STANDARDS.md` | 这个项目的规矩是什么 | 出现新约定时追加 |
| `ROADMAP.md` | 接下来做什么 | 有新想法、完成里程碑时 |

## 文档之间的引用关系

- CHANGELOG 的条目可链接到 ADR / BUGLOG 编号（如 `See ADR-003, BUG-003`）
- BUGLOG 的"根因"若源于某次决策失误，应回链对应 ADR
- ADR 的"后续验证"部分可引用 STANDARDS.md 中的回归清单

## 三条铁律（其余流程均可裁剪，这三条不行）

1. **决策留痕**：重要的"为什么"不写下来，一个月后一定忘，且一定吵架（和未来的自己吵）
2. **变更留痕**：改了什么必须进 CHANGELOG；修了 bug 必须进 BUGLOG
3. **验证留痕**：宣称"修好了/做完了"之前，必须有可复查的验证记录（命令输出或手测清单）
