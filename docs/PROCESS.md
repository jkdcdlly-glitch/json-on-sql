# 标准工作流程（PROCESS）

> 借鉴开源社区的协作流程（RFC/ADR/Code Review），裁剪为"单人 + AI 助手"体量。
> 核心思想：**程序正义**——流程有时难受、滞后，但它是防风险、防浪费、防"拍脑袋"的护栏。

## 0. 体量分级：不是所有事都走全流程

| 级别 | 定义 | 例子 | 走的流程 |
|---|---|---|---|
| **L0 微改动** | 文案、样式微调、注释，不影响行为 | 改个错别字 | 直接改 + CHANGELOG 一行 |
| **L1 常规改动** | 单文件内的小功能/bug 修复 | 修一个渲染 bug | 轻量通道（见 §4） |
| **L2 功能/架构** | 新功能、跨文件改动、方案有取舍 | SQL 引擎升级、i18n 架构 | **完整流程（§1-§6）** |

判断口诀：**会动到数据流/接口/多文件/用户可感知行为 → 至少 L1；有方案取舍 → L2。**

## 1. 提案（Proposal）—— L2 必经

用一段话说清楚五件事（直接写在 review 记录或 issue 里）：
1. **要解决的问题**是什么（现象 + 影响，而不是"我觉得应该改"）
2. **不做会怎样**（不做的代价）
3. **候选方案**至少两个（哪怕第二个是"不修"）
4. **成功标准**：怎么算做完了、怎么验证
5. **影响面**：会碰哪些文件、会不会破坏已有行为

## 2. 讨论（Discussion）—— 有取舍就留痕

- 在 `docs/reviews/` 建一份讨论记录（用 TEMPLATE.md），记下：正反观点、被否掉的方案及否决原因
- 讨论可以口头/脑内进行，但**结论和否决理由必须落盘**——防止一个月后重新争论同一个问题
- 结论格式：`结论：采用方案 B，因为……；代价是……，接受。`

## 3. 决策（Decision / ADR）—— L2 必经

- 结论写入 `docs/decisions/ADR-xxx-标题.md`（用 TEMPLATE.md）
- ADR 状态：`提议 → 已接受 → （可选）已被 ADR-yyy 取代`
- **ADR 不求完备，求"当时为什么"**：半年后看懂取舍逻辑即可

## 4. 实施（Implement）—— 轻量通道在这里

- 实施前先声明：本次属于 L几、涉及哪些文件、预计验证方式
- 编码遵守 `STANDARDS.md` 的项目约定
- **改动过程中如果发现与既有决策冲突，停下来补 ADR，不要边改边推翻**

## 5. 验证（Verify）—— 宣称完成前的硬门槛

- 语法/静态检查：`node --check` 全部 JS
- 逻辑验证：node 脚本实测（构造数据 → 断言输出），或按 STANDARDS.md 冒烟清单手测
- **验证结果要贴出来**（命令 + 输出），"应该没问题"不算验证
- 涉及 bug 修复：按 BUGLOG 对应条目的"防回归要点"复测

## 6. 记录（Record）—— 收尾动作，不可跳过

| 改动类型 | 必写 |
|---|---|
| 功能 | CHANGELOG 一条 |
| Bug 修复 | CHANGELOG 一条 + BUGLOG 完整条目 |
| 决策 | ADR（实施前写） |
| 有价值讨论 | review 记录 |

## 7. 复盘（Retrospective）—— 可选但推荐

出问题（线上 bug、返工、方向性浪费）后问三个问题，写进 reviews/：
1. 这个问题在哪个环节本可以被拦住？
2. 流程缺了什么？是加检查项，还是加文档？
3. 有没有流程是纯负担、可以砍掉的？（流程也要做减法）

## 8. AI 守门规则（Gatekeeper Protocol）

> 分工：人负责方向和最终拍板，AI 负责流程纪律——**AI 是教练和质检员，不是答案机**。
> 类比：孩子直接要答案 vs 目标是学会。本项目目标是"结果正确且过程可复盘"，所以 AI 必须在关键时刻举手。

### 8.1 开工前：五件套声明（L1 及以上必做）

AI 在动手改代码之前，必须先输出（可以很短，但缺一不可）：

1. **问题定义**：要解决什么，判断为 L 几
2. **影响面**：会碰哪些文件、哪些用户可见行为
3. **方案与备选**：打算怎么做、还有什么别的做法、为什么选这个
4. **验证方式**：完成后用什么命令/清单证明做完了
5. **记录计划**：CHANGELOG / BUGLOG / ADR 写哪些

用户说"直接做"时，五件套可以压缩成几行，但 **验证和记录不得省略**。

### 8.2 需求不清：先问后做，禁止硬猜

缺关键信息（数据样例、期望行为、边界条件、取舍偏好）时，AI 必须先提出具体问题。
"大概猜一个"造成的返工，代价高于多问一轮。

### 8.3 红线行为：被要求跳过时必须明示风险

以下三件事即使用户要求跳过，AI 也要先指出后果并给理由；**最终决定权在用户**，但 AI 须在记录中注明"经用户决定跳过"：

- 改完代码不做验证就宣称完成
- 修 bug 不写 BUGLOG
- 推翻已有 ADR 却不更新状态

### 8.4 方向性问题：给选项和利弊，不给唯一答案

用户问"该不该/要不要/怎么选"时，AI 先摆 2-3 个方案的正反与代价，给出倾向但把决策权交回。
（防止"AI 说什么就做什么"的依赖——思路要留在用户脑子里，判断力要留在用户手里。）

### 8.5 完成声明：没有验证输出不算完成

AI 说"完成"时必须附上验证证据（命令 + 输出，或手测清单结果）。
"应该没问题" = 未完成。

---

## 反面清单（这些行为视为违反流程）

- ❌ "我先改着，文档以后补" —— 以后 = 永远不会
- ❌ 一次性改 5 个文件不声明影响面
- ❌ 修 bug 不写 BUGLOG（"这个小不用记"——小的会长大）
- ❌ 用"AI 直接说改好了"替代验证记录
- ❌ 推翻已有 ADR 却不更新 ADR 状态
